# CounselO Legal Updates

Public name: Legal Updates / المستجدات القانونية. Bilingual hubs live at `/legal-updates`, `/ar/legal-updates`, and `/{sa|uae|syr}/[ar/]legal-updates`. Each published item has a stable URL beneath its jurisdiction hub. Existing articles remain in the blog.

## Publication policy

The weekly worker discovers official announcements, retrieves their text, checks relevance and duplication, generates original bilingual analysis, and verifies verbatim evidence against the retrieved snapshot. All items enter **draft** status. A model score is not legal verification. No automatic publication is enabled.

The admin Legal Updates tab displays sources, evidence, the draft in both languages, run outcomes, and failures. Editors may revise language, reject drafts, publish reviewed drafts, or withdraw published updates. Publication requires an entered reviewer name, a substantive note, current revision, affirmative verification, and an unchanged official source snapshot. The designated default reviewer is **Lawyer and Legal Counsel Omar Baghdadi** / **المحامي والمستشار القانوني عمر البغدادي**. The admin reviewer field is prefilled with his name; each publication still requires an explicit review confirmation and note. Choosing a default reviewer does not publish or mark drafts as reviewed. Changes to published content require withdrawal and renewed review. Audit snapshots preserve prior content and actions. Shared-password authentication identifies the authenticated editorial desk; names are attestations, not independently verified individual accounts.

Unknown effective dates stay unknown. Announcement dates are distinct from effective dates and CounselO publication dates. SANA is treated as an official announcement source, not the full operative instrument. A retrieved quotation proves textual presence, not legal applicability; reviewers must check the legal instrument, amendments, commencement, exceptions and Arabic/English meaning. No invented daily notices or seed articles are published.

## Activation

1. Apply `lib/db/migrations/20260912_legal_updates.sql`, then `lib/db/migrations/20260912_legal_updates_editorial.sql` to the intended PostgreSQL database using the deployment database owner. The first migration creates three new tables. The second adds editorial metadata, source-check state and indexes to those tables. Neither changes existing blog, work or service content. Both support repeat application. Do not run schema creation on public requests. The Drizzle schema also declares these tables so future schema tooling recognizes them. RLS is enabled without public policies; the trusted server must use the owning/backend role. Never expose that role to a browser.
2. The selected default model is **GPT-5.6 Luna** (`gpt-5.6-luna`) for discovery and bilingual drafting. Use the existing Replit AI integration (`AI_INTEGRATIONS_OPENAI_API_KEY` and `AI_INTEGRATIONS_OPENAI_BASE_URL`) so usage is billed through Replit. The worker prefers the complete integration pair even when a separate OpenAI key exists. A provider failure never triggers a fallback to another billing account. Direct OpenAI credentials are only used when no integration is configured. The server permits an explicit `LEGAL_UPDATES_MODEL` override; the weekly workflow sets `gpt-5.6-luna` directly. Missing credentials fail visibly; no key is bundled into frontend assets.
3. Deploy the built frontend and API server together using the existing Replit deployment. Deployment is separate from a Git push. Check `/api/legal-updates`, all eight hubs, and `/sitemap-legal-updates.xml` before running discovery.
4. The direct-provider GitHub Actions alternative requires explicit opt-in and its own reachable database and OpenAI billing. Do not use this alternative for Replit-billed AI or copy Replit integration credentials into GitHub. For that alternative, set the repository variable `LEGAL_UPDATES_PROVIDER=openai-direct` and `LEGAL_UPDATES_DATABASE_URL` and `LEGAL_UPDATES_OPENAI_API_KEY`. The model is already set to `gpt-5.6-luna` in the workflow. `.github/workflows/legal-updates-weekly.yml` runs at **08:00 Asia/Tbilisi every Saturday** (04:00 UTC; 07:00 Saudi Arabia/Syria; 08:00 UAE) and supports manual dispatch. This executes the worker directly, so it does not depend on an autoscale web process staying awake or a long HTTP request surviving. The workflow must reach the database. GitHub scheduled execution is best-effort and may be delayed; configure repository workflow-failure notifications.
5. Dispatch once and inspect the admin run report. Resolve failed sources individually before claiming jurisdiction coverage. Publication remains editorially controlled.

Preferred for Replit billing: a managed scheduled job in the Replit environment can execute `pnpm --filter @workspace/api-server legal-updates:run` with the same credentials. A trusted scheduler can also POST `/api/internal/legal-updates/run` with a dedicated `LEGAL_UPDATES_CRON_SECRET` of at least 32 characters; long-request host limits make the CLI preferable. Do not use the shared admin password in an external scheduler.

A PostgreSQL advisory lock prevents concurrent workers. A UTC daily ledger prevents duplicate completed runs on the same day; it also permits an urgent manual run on another day between weekly scheduled runs. Failed/partial runs can be retried; a stale interrupted run becomes retryable after two hours. Exact source URL/content hashes and instrument checks suppress duplicates. Each run selects at most two candidates from each of eleven sources (at most 33 AI requests). Requests, responses, retrieval sizes and output tokens are bounded. Source/AI failures are recorded and never converted into publication. A partial workflow exits nonzero. There is no background `setInterval` in the web server.

## Source coverage and limits

The initial registry includes Saudi justice, official gazette, tax, capital markets, central bank and labor; UAE legislation, tax, central bank and economy; and Syrian official announcements. These are explicitly a starting registry, not every authority or every subnational jurisdiction. Successful retrieval must be checked from the deployment environment. Search UI pages, JavaScript-only pages, PDF-only notices, robots restrictions, redirects outside the exact approved origin and network failures require source-specific adapters or editorial retrieval. The worker does not bypass those restrictions. The discovery window is fourteen days and the weekly selection is intentionally selective, not exhaustive.

Discovery selects this crawler’s robots group (or the wildcard group), applies the longest matching rule with Allow winning ties, and only follows exact approved HTTPS origins. Source HTML is untrusted data. It cannot modify the source allowlist, choose arbitrary retrieval URLs or publish an article. No raw HTML is inserted into article content. The model uses strict structured output; application validation still checks dates, evidence and regional services. See [OpenAI structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

Public API results exclude source snapshots, review notes and evidence quotations. Rendered content includes official attribution, dates, editorial authorship, actual entered reviewer attribution, canonical/hreflang, Article and breadcrumb markup, contextual services and related updates. Source evidence remains accessible only to the authenticated editorial desk. The main deployment serves live update pages and relevant regional homepage/service feeds before the static page cache. A withdrawal removes the item from the public query and sitemap immediately; browser copies already loaded may persist until refresh.

## Rollback

Disable the scheduled workflow first. Withdraw any affected public record through the editorial desk; its audit history remains. Roll back application code if needed while retaining all three tables. Do not drop evidence or audit tables during a routine release rollback.

## Weekly cost policy

The schedule runs once rather than seven times per week: about 86% fewer scheduled executions. With the unchanged cap of 33 AI requests per run, the scheduled weekly request ceiling falls from 231 to 33, excluding manual runs and retries. This is a request-count comparison, not a guaranteed bill reduction: actual cost depends on the configured model, input/output tokens, new developments and retries. Fixed hosting costs are unaffected. The fourteen-day lookback overlaps consecutive weekly runs, but listing truncation, the two-candidate cap per source and inaccessible sources still make discovery selective. Notices may wait up to a week for discovery. Use the manual discovery action for urgent developments; editorial approval remains required.

## Search and editorial lifecycle

Every public article has server-rendered content, a self canonical, reciprocal English/Arabic alternate URLs, publication and modification dates, source attribution, visible breadcrumbs and matching structured data. Reviewer markup reflects the stored review attestation; Omar’s profile is linked only when the stored reviewer matches his designated name. Article imagery is optional and must represent the development; no generic logo is passed off as an article photograph.

Practice hubs only exist when published updates use a valid regional service. Contextual service links and up to five bilingual legal-matter links connect updates with useful next steps. Invalid articles, empty out-of-range archives and unknown practice routes return 404 with noindex. Content stays available to crawlers in initial HTML; there is no special markup that guarantees AI citations or search placement.

A bounded rolling source check inspects up to 25 published official sources per run, prioritizing the oldest check and those not checked in seven days. It records unchanged, changed or unavailable status. This is a source-text comparison, not a renewed legal review. The public page explicitly distinguishes the two. Large backlogs may take multiple weekly runs. A changed source never silently rewrites or republishes an article.

Corrections require a bilingual correction note and renewed review after withdrawal. Audit records retain prior content; only the correction text and publication date appear publicly. Superseded updates remain addressable with an explicit notice and a link to a later, already-published update in the same jurisdiction. Related legal-matter links must resolve in both languages. Representative images require bilingual descriptive alternatives. Every Arabic public field is checked for Arabic content; semantic equivalence and legal applicability still require the reviewer.
