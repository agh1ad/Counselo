## Acquisition and privacy boundaries

`page_location` contains only a public path on the canonical host. Known search/AI/social referrers become fixed origins (for example `https://www.google.com/`), preserving a traffic-source signal without referring paths, queries or arbitrary subdomains. Explicit allowlisted UTM source/medium values populate the GA4 campaign fields; organic referrers are not relabeled as campaigns. Arbitrary campaign names, terms, unknown sources/referrer domains and click IDs are not copied into application analytics. This is deliberately less detailed than unconstrained campaign collection; review any paid-campaign reporting needs before relying on campaign-name or click-ID attribution. An AI source label means a referral from that source, not evidence that an AI engine cited the site.

The application stores a separate first-landing record for the current browser tab: public path, coarse source and coarse medium. It travels with the contact request and is validated server-side. This is first-touch tab attribution, not GA4 session attribution or proof of incremental conversion. Cookies/referrer restrictions, blocked analytics and direct navigation can reduce attribution. Unknown referring domains are represented as `external_referral` in this coarse record. The data-layer envelope is cleared before every event so previous lead IDs or service parameters cannot leak into later events. Analytics script injection is limited to the two production hostnames; local browsers can inspect queued events without sending production traffic.

## Enquiry outcomes and storage

Contact name, email, phone, message and attachments remain operationally required/handled as before. Attribution, a random lead ID and the outcome are placed inside the existing encrypted payload. No table, column, migration, RLS policy or secret is added. Client-submitted lead IDs/outcomes are stripped. An authenticated admin opens one request's attribution and can explicitly save `new`, `qualified`, `not_qualified`, `engaged`, or `closed`. The PATCH endpoint requires existing admin authentication and same-origin headers, locks one row for the short decrypt/update/encrypt transaction, and changes only the encrypted payload and update timestamp. API responses project attribution/outcome only, excluding client narrative and documents.

Qualification means a reviewed enquiry is relevant, within an available service scope and suitable for follow-up. Engagement is recorded separately; neither is inferred from clicks. These outcomes are durable across browsers, but this screen is a latest-100 request workflow, not a complete sitewide KPI dashboard. Existing requests retain unknown attribution/no join ID; historical values are not fabricated. There is no automatic upload of qualification to GA4. A future authorized report can calculate qualification by the stored landing/source fields directly, or join a controlled GA4 event export using the random lead ID.

## Verification boundaries

Regression checks cover actual envelope dispatch, event field exclusion and clearing, damaged local-counter storage, recognized referrer/campaign sanitization, delayed SPA metadata, effect replay/cancelled navigation, server validation/encryption/backward compatibility, and HTTP admin/origin/outcome persistence with an in-memory database fixture. The HTTP fixture performs no external database or notification operation. Local checks do not prove published GTM acceptance, GA4 collection, production contact delivery, search ranking or AI citations. Those require the live cutover checks above.

The API and frontend use the existing backend and form conventions. Admin SEO and GTM cards now say that current verification is required, instead of displaying permanently green completion claims. Browser-only counters remain explicitly browser-only.
